API 与批量生成：并发、限流、重试、预算

批量不是“写个循环”。并发、限流、重试、幂等、预算五件事先设计，否则一半费用花在重复请求和失败重跑。

适用与不适用 / Fit and no-fit

  • 一天几十/几百条素材的批量生产。
    Batch production of dozens/hundreds of assets per day.
  • 需要 API 接入、队列、重试、成本控制的团队。
    Teams integrating APIs, queues, retries and cost control.
  • 不适用：一天 1–2 条、手工生成。
    Not for: one or two clips per day, manual generation.

怎么做 / Do this

  1. 先做幂等键：项目+镜头+版本+参数。
    Create an idempotency key: project+shot+version+params.
  2. 并发按供应商限流，不按你的机器。
    Set concurrency by vendor limits, not your machine.
  3. 失败重试分级：429 退避，5xx 重试，4xx 不重试。
    Tiered retries: 429 backoff, 5xx retry, 4xx no retry.
  4. 每条请求写成本字段；超预算停。
    Log cost per request; stop at budget.
  5. 产物落盘 + manifest，不依赖 URL。
    Persist outputs + manifest; do not rely on URLs.

别踩 / Avoid

  • 无幂等；重试产生重复扣费。
    No idempotency; retries double-charge.
  • 并发拉满；429 后全部失败。
    Max concurrency; 429 kills the batch.
  • 只存 URL；链接过期后素材丢失。
    Storing URLs only; expired links lose assets.

继续往下 / Go deeper

批量生成的成本失控，通常不是单价高，是重复请求。一次网络超时，客户端重试，供应商其实已经成功；没有幂等键，你为同一条付了两次。先把幂等键写进请求头/参数，再写重试。

429 不是故障，是限流信号。正确做法是指数退避 + 队列排队，不是加机器/加并发。并发越高，429 越多，重试越多，成本越高；这是负反馈。

验收 / Checks

  • 每条请求有幂等键和成本字段。
    Every request has idempotency key and cost.
  • 并发/重试策略写在代码里，不靠人盯。
    Concurrency/retry in code, not manual watch.
  • 产物落盘 + manifest 可追溯。
    Outputs persisted + traceable manifest.
  • 超预算自动停，不刷爆卡。
    Budget cap stops the batch.
