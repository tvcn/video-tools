API and batch generation

Batch is not a loop. Design concurrency, rate limits, retries, idempotency and budget first, or half the spend goes to duplicate requests and failed reruns.

Fit and no-fit / 适用与不适用

  • Batch production of dozens/hundreds of assets per day.
  • Teams integrating APIs, queues, retries and cost control.
  • Not for: one or two clips per day, manual generation.

Do this / 怎么做

  1. Create an idempotency key: project+shot+version+params.
  2. Set concurrency by vendor limits, not your machine.
  3. Tiered retries: 429 backoff, 5xx retry, 4xx no retry.
  4. Log cost per request; stop at budget.
  5. Persist outputs + manifest; do not rely on URLs.

Avoid / 别踩

  • No idempotency; retries double-charge.
  • Max concurrency; 429 kills the batch.
  • Storing URLs only; expired links lose assets.

Go deeper / 继续往下

Batch cost blowups are usually duplicate requests, not high unit price. A timeout triggers a client retry while the vendor already succeeded; without idempotency you pay twice. Put the key in headers/params before retries.

429 is a rate-limit signal, not a failure. Exponential backoff and a queue, not more machines/concurrency. Higher concurrency means more 429s, more retries, higher cost: negative feedback.

Checks / 验收

  • Every request has idempotency key and cost.
  • Concurrency/retry in code, not manual watch.
  • Outputs persisted + traceable manifest.
  • Budget cap stops the batch.
